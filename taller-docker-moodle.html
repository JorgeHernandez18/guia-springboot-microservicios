Taller de Docker para microservicios

En el laboratorio anterior construyeron Catálogo y Pedidos y los corrieron a mano, cada uno en su terminal. Hoy los empaquetan en contenedores y levantan el sistema completo con un solo comando. Así se despliegan los microservicios en la industria.

Modalidad: en parejas, a su ritmoTiempo estimado: 2 a 3 horasEntrega: en Moodle, antes de la próxima clase

Imagen

El paquete inmutable con su aplicación y todo lo que necesita para correr: Java, el jar, la configuración.

Contenedor

Una imagen en ejecución. De una imagen pueden correr muchos contenedores iguales.

Dockerfile

La receta para construir una imagen, paso a paso.

Compose

Un archivo que describe varios contenedores y los levanta juntos, en una misma red.

6

Paso 6. Entiendan por qué localhost ya no sirve

En el laboratorio, Pedidos llamaba a http://localhost:8081. Dentro de un contenedor, localhost es el propio contenedor, no su computador. Pedidos buscaría a Catálogo dentro de sí mismo y respondería 503.

La solución es la red de Docker Compose: cada servicio se alcanza por su nombre. Pedidos llamará a http://catalogo:8081.

No hay que tocar Java. En el laboratorio la dirección quedó en configuración (catalogo.url), y Spring Boot permite reemplazar cualquier propiedad con una variable de entorno: catalogo.url se escribe CATALOGO_URL. Eso es lo que hará Compose.

2. Usen este compose en lugar del anterior

Catálogo ahora tiene su propia base de datos PostgreSQL, en su propio contenedor, con un volumen que guarda los datos en disco. Las variables SPRING_DATASOURCE_* reemplazan la configuración de H2 sin tocar application.properties.

3. Prueben la persistencia

Con PostgreSQL, Spring no ejecuta data.sql, así que el catálogo arranca vacío. Creen dos productos con POST /productos, ejecuten docker compose restart catalogo y listen otra vez: deben seguir ahí. Incluso con docker compose down y up los datos se conservan, porque viven en el volumen. Solo docker compose down -v los borra.

Si Catálogo falla al arrancar porque PostgreSQL todavía no está listo, restart: on-failure lo vuelve a intentar solo. Es otra cara de la pregunta 5.

Si algo falla

Cannot connect to the Docker daemon
Docker Desktop no está abierto. Ábranlo y esperen a que diga que está corriendo.
Bind for 0.0.0.0:8081 failed: port is already allocated
El puerto está ocupado: probablemente el servicio sigue corriendo con mvnw o quedó otro contenedor. Deténganlo, o ejecuten docker compose down.
release version 21 not supported al construir
Su proyecto usa una versión de Java distinta a la imagen. Igualen el número de las líneas FROM con <java.version> del pom.xml.
no main manifest attribute o Unable to access jarfile
La compilación no generó el jar de Spring Boot. Revisen que el pom.xml tenga el plugin spring-boot-maven-plugin (Spring Initializr lo incluye).
Pedidos responde 503 con todo arriba
Revisen que CATALOGO_URL diga http://catalogo:8081, con el mismo nombre del servicio en compose.yaml, y que Catálogo ya haya terminado de arrancar (docker compose logs catalogo).
Los cambios en el código no aparecen
Docker usa la imagen ya construida. Ejecuten docker compose up --build para reconstruir.
El build tarda muchísimo
La primera vez descarga imágenes y dependencias. Las siguientes son más rápidas porque Docker guarda en caché la capa de dependency:go-offline.
